# Verification tier proposal: an independent cloud check after L1 to L3 pass

Status: PROPOSAL, 2026-11-02. Nothing here has run. No cloud call has been made for it. The operator must approve the
design and the live run (section 3) before anything runs.

Request (operator, for Prof. Hao: a path from the 99% rescue rate to catching every failure): after the post-run check (src/dse/post_run_check.py,
layers L1 to L3, L3 in src/dse/l3_invariants.py) passes a local result, run one independent cloud check before the
result is accepted. Find the CHEAPEST check that can catch a wrong final state.

## 2. What the verifier sees (all candidates)

Built only from what the client holds at the end of the turn. Never the Task object, `task.reference`, `check_task`,
`expected`, `end_state_ok`, `state_ok`, `answer_ok` or the grader's `end_state_diff`.

1. The task text of the turn (the user message, without the context filler).
2. The standing instructions (first user message) and rules 6 to 8 (harness/evalset_env.py::RULES_678_TEXT).
3. A snapshot of the current state before the turn, `env_before`, in the directory format
   (evalset_env.directory_text), with every `api_token` value replaced by `[REDACTED]`.
4. The turn's tool calls, in order, each with its tool result.
5. The final answer text.
6. The change set: for every record the turn changed (`env_diff(env_before, env_after)`, i.e. before vs after, NOT
   expected vs actual), the record before and after.

Output: JSON `{"verdict": "accept" | "reject", "reason": "<one sentence naming the record or value>"}`. Reject means
rollback (SnapshotLog, USD 0) and the existing Sonnet escalation under the per-task budget.

A unit test must enforce the isolation: the payload builder takes (task text, standing instructions, env_before, calls
with results, final text) and nothing else, and does not import `check_task` or touch `Task.reference`.

**Payload size [PLANNING]**, over all 750 recorded task turns, rebuilt offline the way scripts/cloud_redo.py::rebuild
does: static part (verifier instruction of about 1,400 chars, standing instructions, rules) 2,483 chars; per-turn part
(snapshot, task text, calls with results, final text, change set) median 4,435 chars, p90 4,965, max 6,165. Tokens per
char: 0.4521 provider input tokens per char (median over 80 first calls of the full-history redo, provider usage vs the
rebuilt prompt's chars, range 0.4415 to 0.4688). That prompt is dominated by random filler text, which tokenizes
densely, so it is used here as the HIGH side of the conversion. Resulting tokens: static 1,123 (above the 512-token
minimum cacheable prefix for claude-haiku-5-5 and claude-sonnet-5-5, quoted in
results/cloud_prices_anthropic_20261014.json), per-turn median 2,005, p90 2,245, max 2,787.

**Pricing basis** [REG cloud-prices-anthropic], USD per MTok: claude-haiku-5-5 input 0.1, 5m cache write 0.125, cache
read 0.01, output 0.5; claude-sonnet-5-5 input 2, 5m cache write 2.5, cache read 0.1, output 10. Rolling breakpoint
(src/cloud/prompt_cache.py): breakpoint on the system prompt (read after the session's first verifier call) and on the
latest message (written). Each verifier call carries a different snapshot, so only the static prefix is read; the
per-turn part is written at the cache-write rate. Assumption, as in every rolling-cache row: verifier calls of a
session under 5 minutes apart. Local turns take a median of 9.67 s to 27.27 s per task [REG task-latency-by-policy], so
consecutive verifier calls are well inside that lifetime.

Three price points per check, each [PLANNING] on the token sizes above:

- **billed point**: static read, median per-turn part written, 100 output tokens.
- **high**: cold cache (static and p90 per-turn part both written), output at the cap.
- **upper bound**: the largest recorded prompt (3,910 tokens) all at the write rate (which is above the uncached input
  rate), output at the cap.

Reference bill: all-cloud B3 v2 on claude-sonnet-5-5 under the rolling breakpoint, USD 0.00936/task, 90/90 correct
[REG all-cloud-b3-cost-rolling-cache]; on claude-haiku-5-5, USD 0.00063/task, 87/90 correct [REG
all-cloud-b3-cost-rolling-cache, all-cloud-b3-quality].

## 3. Candidate checks, cheapest first

Latency basis [REG task-latency-by-policy, all-cloud-b3-cost]: an all-cloud B3 v2 task takes a median of 2.50 s on
claude-haiku-5-5 and 4.59 s on claude-sonnet-5-5, over a mean of 2.08 and 2.12 calls per task. A verdict is one call
with a short output, so its latency should be below those per-task medians; roughly one call's share, about 1.2 s
(Haiku) and 2.2 s (Sonnet) [REG-DERIVED: median seconds per task / mean calls per task]. That is an estimate; only the
live run measures it.

### (0) Zero-cost alternative noted for completeness: more L3 rules

Not a cloud check, and it costs USD 0, but the 11 accepted wrong turns above show which deterministic rules would
have fired: an "every open X" set-completeness check against the current state (8 of 11: the ticket tasks), a
"state-changing call returned status error and the answer admits failure" check (inv_price), an answer-admits-failure
check on information tasks (led_balance_info), and a literal comparison for "content is exactly: ..." (file_write).
These rules would be written AFTER seeing the misses, so any replay of them on these seeds is tuned on its own test set;
they can only be judged on new seeds. Listed so the operator can weigh it; it is not the recommendation for this request.

### (a) Haiku verdict on the change set vs the task request (claude-haiku-5-5)

- Sees: section 2, items 1 to 6. Thinking off, max_tokens 256.
- Outputs: accept/reject plus a one-sentence reason.
- Tokens [PLANNING]: input median 3,128 (1,123 static + 2,005), max 3,910; output about 100, cap 256.
- USD per verified task [PLANNING]: billed point 0.000312; high 0.000549; upper bound 0.000617. Billed point is 3.3% of
  the Sonnet all-cloud per-task bill (0.000312 / 0.00936).
- Added latency: about 1.2 s median (estimate above), against a local turn of 9.67 s to 27.27 s.
- Why it can catch a wrong final state: every one of the 11 accepted wrong turns is visible from items 1 to 6 alone.
  The ticket misses show as an open ticket in the snapshot that matches the task's filter but is absent from the change
  set; inv_price shows as an error result plus a change to a field the task did not name; led_balance_info as an answer
  with no balance while the snapshot holds it; cal_default_len (the cloud failure) as a duration that differs from the
  standing instruction. Checking a short change set against a stated request is a narrower job than doing the task,
  which is why a small model is a reasonable first candidate.
- Weakness: a small judge may accept plausible-looking results (false accepts) or reject correct ones on wording;
  file_write's missing trailing period is the hardest case (both qwen3:14b and the Sonnet redo got it wrong in the same
  way, see section 4).

### (b) Sonnet verdict on the same input (claude-sonnet-5-5)

- Sees and outputs the same as (a). Thinking off, max_tokens 256 (a thinking variant would add its thinking tokens at
  USD 10 per MTok output: about USD 0.01 per 1,000 thinking tokens).
- USD per verified task [PLANNING]: billed point 0.006125; high 0.01098; upper bound 0.01234. Billed point is 65% of the
  Sonnet all-cloud per-task bill (0.006125 / 0.00936).
- Added latency: about 2.2 s median (estimate above).
- Tradeoff: likely a better judge than Haiku, but paying 65% of an all-cloud task on every locally accepted task
  removes most of the hybrid's saving. Only worth it if (a) misses its targets and Sonnet clearly meets them.

### (c) Re-derivation: the cloud computes the expected end state independently, local code compares

- Sees: items 1 to 3 only (task text, standing instructions and rules, current-state snapshot with phone numbers added
  for the information tasks, secrets redacted). It does NOT see the local calls, answer or change set.
- Outputs: the tool calls it would make (state-changing calls with arguments) and, for an information task, the answer
  value. Local code then applies those calls to a copy of `env_before` and compares the result with the local
  `env_after`, and compares answer values. Any difference is a reject. The comparison is deterministic and uses no
  reference calls; it is the cloud's derivation, not the grader's.
- Tokens [PLANNING]: input median 2,766 (1,123 static + 1,643 per turn), max 2,900; output 375 per task, the all-cloud
  B3 v2 mean (33,726 output tokens over 90 tasks on claude-haiku-5-5 and 33,718 on claude-sonnet-5-5 [REG-DERIVED
  all-cloud-b3-cost]), cap 1,024.
- USD per verified task [PLANNING]: Haiku billed point 0.000404, high 0.000865, upper bound 0.000875 (4.3% of the Sonnet
  all-cloud bill); Sonnet billed point 0.00797, high 0.0173, upper bound 0.0175 (85% of the Sonnet all-cloud bill).
- Added latency: close to a whole all-cloud task (it does the task's reasoning): about 2.50 s Haiku, 4.59 s Sonnet
  [REG task-latency-by-policy medians].
- Tradeoffs: it needs no judgement of the local trace, so it is not fooled by a confident local answer, and its recall
  on wrong local results is at least the cloud's own task accuracy. But its false-escalation rate is at least the
  cloud's own error rate on correct local results (Haiku all-cloud 87/90 [REG all-cloud-b3-quality]), it misses errors
  the cloud makes in the same way as the local model, and in Sonnet form it costs about as much as simply running the
  task in the cloud. A task with several valid end states (none in B3 v2, whose grader assumes one) would need an
  equivalence rule.

## 4. Recommendation: (a), the Haiku verdict, with (c)-Haiku measured beside it

Recommended: **(a) a claude-haiku-5-5 verdict on the change set vs the task request**, run only on results L1 to L3
accept, reject leading to rollback and the existing Sonnet escalation under the USD 0.25 per-task cap
(src/cloud/task_budget.py).

- It is the cheapest cloud check: about USD 0.0003 per verified task at the billed point, and at most about USD 0.0006
  at the upper bound [PLANNING], which is 3.3% (point) of the Sonnet all-cloud per-task bill.
- It can catch a wrong final state because the wrong state is in its input: the before/after records of everything the
  turn changed, the current state of everything it could have changed, and the request. In every one of the 11 accepted
  wrong turns, the error can be read from those inputs without the reference calls (section 3a).
- Re-derivation with Haiku costs almost the same (USD 0.000404 point) and fails in a different way (it errs when the
  cloud cannot do the task, while a verdict errs when the judge is fooled), so the live run should measure both arms on
  the same turns for under USD 1 more (section 5). Run the Sonnet forms only if both Haiku arms miss the targets.
- Applied to the cloud's own escalated result too (same payload, from the cloud's trace), it is the only candidate
  route to the 2 remaining cloud failures; whether it catches them is unmeasured.

Expected hard case: `file_write` seed 20260904 turn 24. The task text is "...whose content is exactly: Handover note
856: rotate on-call to the next engineer. Also, recall ..."; the expected content ends with the period, and the local
model wrote it without. The full-history Sonnet redo of that turn was also wrong, with the same end-state diff path
(files//srv/notes/handover_82.txt/content), read from results/cloud_redo_full_context_v1*.jsonl. An LLM judge may well
accept it; a literal string rule (candidate 0) would not.

## 5. What a USD 0 replay can and cannot measure

**It cannot produce a single new verifier verdict.** No recorded file holds a cloud judgement of a local trace, so
recall, false escalations and latency of (a) and (b) are unmeasurable without calls. What recorded data can stand in:

1. **CEILING, perfect verifier, standalone over the 197** (rejects exactly the wrong turns, accepts every correct one):
   escalated turns then take their recorded rescue outcome: 195/197 [REG cloud-rescue-combined], with that row's
   STAND-IN caveat for the 28 rollback redos. This is the best any verifier can do with the current escalation path,
   not a verifier measurement.
2. **CEILING, perfect verifier in the post-L3 pipeline** (three replayed tiers): the 11 accepted wrong turns escalate.
   [PLANNING] from the full-history redo rows: 10 of the 11 are fixed (all but file_write seed 20260904 turn 24), so
   final accuracy would go from 147/150 to 150/150 (ollama_ctx_8192) and from 142/150 to 149/150 (ollama_default), and
   stay 149/150 (ollama_ctx_4096) [REG post-run-check-* for the starting points]. The redo spend of those 11 turns is
   USD 0.3865 billed (0.9358 all input uncached) [PLANNING]. The perfect-oracle row for seeds 20260901 to 20260903 is
   already registered: 90/90 at ollama_ctx_8192 and ollama_ctx_4096 [REG hybrid-local-first-rollback, "ceiling, oracle
   signal"]. Label: CEILING.
3. **PROXY for (c) re-derivation recall, from the full-history Sonnet redo**: the redo IS a cloud derivation of the
   turn from the same `env_before` (with full history and live tools, not the snapshot-only single call proposed). Over
   the 197: in 167 the redo's end state equals expected and the local one does not, so they differ; of the 30 redo
   failures, 29 have a different set of end-state diff paths from the local turn, so the states differ too; the 1 left
   (file_write, same path) cannot be decided from recorded fields [PLANNING, read from the redo and local rows]. So a
   Sonnet re-derivation proxy would flag at least 196/197. Label: PROXY, an upper-side estimate for a snapshot-only
   call, and it uses the grader's flags only to infer "differs", never as verifier input.
4. **PROXY for (c) false escalations**: the all-cloud runs give the cloud's own error rate on these tasks: Sonnet 90/90,
   Haiku 87/90 [REG all-cloud-b3-quality]. A re-derivation that errs where the local model was right is a false
   escalation, so Haiku's 3/90 is a rough floor for Haiku (c)'s false-escalation rate. Label: PROXY (the all-cloud runs
   used the cloud's own history and environment, not the local `env_before`).
5. **PRICED, NOT RUN**: payload sizes and USD per task (sections 2 and 3).

Nothing in recorded data stands in for an LLM-judge verdict. Simulating (a) or (b) from the redo outputs would be
measuring re-derivation and calling it a verdict; this proposal does not do that.

## 6. Pre-registration draft (to move into docs/EXPERIMENTS.md once approved)

**Hypothesis.** A claude-haiku-5-5 verdict on the change set catches most wrong local results that L1 to L3 accept, at
a small fraction of the all-cloud bill, with few false escalations.

**Data.** Section 5 Run V1. Prompt text frozen and committed before the first call. Verifier payload builder unit-tested
for grader isolation (section 2). Grading of the verifier: its verdict vs the recorded `end_state_ok` (the grader is
used only to score the verifier, never as its input).

**Seeds / held-out split.** Development seeds 20260901 to 20260904; held-out seed 20260905 (the same split as
post-run-check-tuned). The prompt is frozen, so the first pass is evaluated on all five seeds. At most one amendment
(prompt change), decided on seeds 20260901 to 20260904 only, then evaluated on seed 20260905 alone; the held-out figure
is the headline for an amended prompt.

**Targets** (per arm; met or missed reported as is):

| metric | target |
|---|---|
| failures caught, standalone, out of 197 | >= 187/197 |
| failures caught, post-L3 positives (11 B3 v2 + 5 q4_0 28928) | >= 14/16 |
| false escalations, standalone (verifier rejects a correct local result), out of 553 | <= 28/553 |
| false escalations, post-L3 negatives (168 B3 v2 + 76 q4_0 28928) | <= 12/244 |
| added USD per verified task, billed | <= USD 0.001 |
| added latency per verified task, median | <= 3 s |
| new correct/90, q4_0 28928 operating point (now 85/90 [REG operating-point-q4-28928]), rejected turns graded from redo rows or IMPUTED as in hybrid-full-pipeline-v1 | >= 88/90 |
| % of the Sonnet all-cloud bill for that pipeline (now 43.4% [REG operating-point-q4-28928-rolling-cache]) | <= 75% |

The 75% allows for the added escalations at the imputed USD 0.04065 per escalation [REG
operating-point-q4-28928-rolling-cache]; it is a budget line, not a prediction.

**Wording rules.** Never write a percentage of one hundred for any catch or accuracy figure. Report counts ("x/197"). Only if a run shows 197/197 caught may a report say
"every failure in our test suite caught", and then only with the test suite named (B3 v2, qwen3:14b, these seeds).
A catch is a catch by the verifier; whether the escalation then fixes it is reported separately (the rescue rows).

**Stop rules.**

- Job cap USD 2.00 billed, enforced in code (client spend cap = ledger total + 2.00); per-task verifier cap USD 0.005
  (about 8 times the arm (a) upper bound), via BudgetedClient; no call is sent whose reservation would pass either.
- Stop the arm after 5 replies with no parseable verdict (or, for (c), no parseable call list), or 5 provider errors.
- Futility: after the development seeds, if an arm's false escalations on the 553 standalone negatives (development
  share) pass 10%, stop that arm; it cannot meet the target without an amendment.
- No Sonnet call in V1. V2 only with its own approval.
- No local model calls and no evo-x2 time: everything is rebuilt from recorded files.

**Not claimed even if all targets are met.** A live hybrid result (the replay assumes a task's local outcome does not
depend on earlier escalations, as every post-run-check row states); results for other models, runtimes or long tasks;
anything about the 64 wrong turns of the two tiers without post-run check rows beyond the standalone figure.

## 7. Open questions for the operator
