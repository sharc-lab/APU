## 2. What the verifier sees

Built by src/dse/verification_tier.py from what the client holds at the end of the turn
(analysis/verification_tier_plan.py::client_view, from grader-stripped turn rows). Never the Task object, its reference
calls or expected answer values, `check_task`, `expected`, `end_state_ok`, `state_ok`, `answer_ok` or the grader's
`end_state_diff`.

System part (identical for every call of one session, so it is the cached prefix): the frozen verifier instruction,
the standing instructions, and rules 6 to 8 (harness/evalset_env.py::RULES_678_TEXT). User part:

1. The task text of the turn with the recall-probe suffix stripped (decision 2), without the context filler.
2. The state before the turn in the directory format (evalset_env.directory_text), header "state before this turn".
3. The turn's tool calls, in order, each with its tool result (each applied to a copy of the pre-turn state, as the
   local harness did).
4. The final answer text.
5. The change set: every record the turn changed (before vs after, NOT expected vs actual), and any email added to the
   outbox.

Every api_token value is replaced by `[REDACTED]` anywhere in the user part. Output: JSON `{"verdict": "accept" |
"reject", "reason": "<one sentence naming the record or value>"}`. Reject means rollback (SnapshotLog, USD 0) and the
existing Sonnet escalation under the USD 0.25 per-task cap.

Isolation tests (tests/test_verification_tier.py): the builder imports nothing from the harness and names no grader
field (static, as tests/test_post_run_check.py does for L3); its signatures take no Task object; every payload of the 260
accepted turns carries no grader field name; with the grader fields of the rows and the session's reference calls and
answer values replaced by a sentinel, the payload is unchanged and carries no sentinel; the recall-probe suffix is
stripped on every probe turn of all five seeds (and the template equals the harness's own); no secret value is in any
payload; the system part is at least the 512-token minimum cacheable prefix and identical within a session.

**Pricing basis** [REG cloud-prices-anthropic], USD per MTok: claude-haiku-5-5 input 0.1, 5m cache write 0.125, cache
read 0.01, output 0.5; claude-sonnet-5-5 input 2, 5m cache write 2.5, cache read 0.1, output 10. Rolling breakpoint
(src/cloud/prompt_cache.py): breakpoint on the system prompt (written on a session's first verifier call, read after)
and on the user message (written on every call; each turn's user message differs, so it is never read back).
ASSUMPTIONS: verifier calls of one session under 5 minutes apart; output 100 tokens per verdict at the billed point, the
cap (256) at high and upper bound [REG verification-tier-payload-cost]. Local turns take a median of 9.67 s to 27.27 s
per task [REG task-latency-by-policy], so consecutive verifier calls are well inside the cache lifetime.

Price points per verified task [REG verification-tier-payload-cost]: **billed point** (static read, median turn part
written, 100 output tokens, median ratio); **high** (cold cache, p90 turn part, output at the cap, largest ratio);
**upper bound** (largest prompt all at the write rate, output at the cap, largest ratio).

Reference bill: all-cloud B3 v2 under the rolling breakpoint, claude-sonnet-5-5 USD 0.00936/task, 90/90 correct;
claude-haiku-5-5 USD 0.00063/task, 87/90 correct [REG all-cloud-b3-cost-rolling-cache, all-cloud-b3-quality].

## 3. Candidate checks, cheapest first

Latency basis [REG task-latency-by-policy, all-cloud-b3-cost]: an all-cloud B3 v2 task takes a median of 2.50 s on
claude-haiku-5-5 and 4.59 s on claude-sonnet-5-5, over a mean of 2.08 and 2.12 calls per task. A verdict is one call
with a short output; roughly one call's share is about 1.2 s (Haiku) and 2.2 s (Sonnet) [REG-DERIVED: median seconds
per task / mean calls per task]. That is an estimate; only the live run measures it.

### (0) Zero-cost alternative noted for completeness: more L3 rules

Not a cloud check, and it costs USD 0. The 16 accepted wrong turns show which deterministic rules would have fired: a
"request says leave closed X alone and a closed X changed" check (the 8 ticket turns of B3 v2 and 3 of q4_0 28928, by
the registered analysis above), a "state-changing call returned an error and nothing changed" check (inv_price), an
answer-admits-failure check on information tasks (led_balance_info), and a literal comparison for "content is exactly:
..." (file_write). These rules would be written AFTER seeing the misses, so any replay of them on these seeds is tuned
on its own test set; they can only be judged on new seeds. Still open (operator question 4).

### (a) Haiku verdict on the change set vs the task request (claude-haiku-5-5): APPROVED

- Sees: section 2. Thinking off, max_tokens 256.
- Tokens [REG verification-tier-payload-cost]: input median 3,638 (static system part 900, turn part median 2,738, p90
  2,997, max 3,931), largest prompt 4,831; output 100 ASSUMED, cap 256.
- USD per verified task [REG verification-tier-payload-cost]: billed point 0.000401; high 0.000631; upper bound
  0.000752. Billed point is 4.3% of the Sonnet all-cloud per-task bill [REG-DERIVED: 0.000401 / 0.00936,
  all-cloud-b3-cost-rolling-cache].
- Added latency: about 1.2 s median (estimate above), against a local turn of 9.67 s to 27.27 s.
- Why it can catch a wrong final state: in every one of the 16 accepted wrong turns, the error is in its inputs
  [REG verification-tier-accepted-wrong]: 11 of them show a closed ticket in the change set whose closed status is in
  the pre-turn state; inv_price shows an error result and no change to the named record; led_balance_info shows an
  answer without the balance the pre-turn state holds; file_write shows content that differs from the request's text
  by its last character. Checking a short change set against a stated request is a narrower job than doing the task.
- Weakness: a small judge may accept plausible-looking results (false accepts) or reject correct ones on wording;
  file_write's missing trailing period is the hardest case (both qwen3:14b and the Sonnet redo got it wrong in the same
  way, section 4).

### (b) Sonnet verdict on the same input (claude-sonnet-5-5): not in Run V1

- USD per verified task [REG verification-tier-payload-cost]: billed point 0.007935; high 0.012624; upper bound
  0.015032. Billed point is 85% of the Sonnet all-cloud per-task bill [REG-DERIVED: 0.007935 / 0.00936].
- Added latency: about 2.2 s median (estimate above).
- Paying 85% of an all-cloud task on every locally accepted task removes most of the hybrid's saving. Only worth it if
  (a) misses its targets and Sonnet clearly meets them (Run V2, its own approval).

### (c) Re-derivation: the cloud computes the expected end state independently, local code compares: comparison only

- Sees: task text (suffix stripped), standing instructions and rules, and the pre-turn state with every field (phone
  numbers and file contents included, secrets redacted). Not the local calls, answer or change set. Outputs the
  state-changing calls it would make and, for a question, the answer value; local code applies those calls to a copy of
  the pre-turn state and compares with the local end state. The comparison uses no reference calls.
- Tokens [REG verification-tier-payload-cost]: input median 4,557, max 4,768; output 375 (the claude-haiku-5-5
  all-cloud B3 v2 mean, 33,726 output tokens over 90 tasks), cap 1,024.
- USD per verified task [REG verification-tier-payload-cost]: Haiku billed point 0.000673, high 0.001121, upper bound
  0.001128 (7.2% of the Sonnet all-cloud bill [REG-DERIVED: 0.000673 / 0.00936]); Sonnet billed point 0.013383, high
  0.022429, upper bound 0.022551 (above the Sonnet all-cloud bill itself).
- Tradeoffs: not fooled by a confident local answer, but its false escalations are at least the cloud's own error rate
  on correct local results (Haiku all-cloud 87/90 [REG all-cloud-b3-quality]), and it misses errors the cloud makes the
  same way as the local model. The 2026-11-02 draft's recall proxy for (c) from the redo rows was a throwaway figure; it
  is not registered and is withdrawn (arm (c) is not in the approved run).

## 5. What a USD 0 replay can and cannot measure

**It cannot produce a single verifier verdict.** No recorded file holds a cloud judgement of a local trace, so recall,
false escalations and latency of (a) are unmeasurable without calls. What recorded data gives:

1. **CEILING, perfect verifier, standalone over the 197**: 195/197 [REG cloud-rescue-combined], with that row's
   STAND-IN caveat. Under decision 3 and the post-L3 design this is not reachable by Run V1; it is listed as context.
2. **CEILING, perfect verifier in the post-L3 pipeline** [REG verification-tier-ceiling]: the accepted wrong turns
   escalate and take their recorded outcome. ollama_ctx_4096 stays 149/150; ollama_ctx_8192 147/150 -> 150/150 (3 of 3
   fixed, escalation USD 0.0552 billed, 0.1151 upper bound); ollama_default 142/150 -> 149/150 (7 of 8 fixed, not
   fixed: file_write seed 20260904 turn 24; USD 0.3313 billed, 0.8207 upper bound); q4_0 28928 85/90 -> 90/90 (5 of 5,
   IMPUTED from all-cloud outcomes, USD 0.2045). Label: CEILING. The perfect-oracle row for seeds 20260901 to 20260903
   is also registered [REG hybrid-local-first-rollback, "ceiling, oracle signal"].
3. **PRICED, NOT RUN**: payload sizes and USD per task (sections 2 and 3).

Nothing in recorded data stands in for an LLM-judge verdict. Simulating (a) from the redo outputs would be measuring
re-derivation and calling it a verdict; this design does not do that.
