# Failure-mode map: what happens when memory runs out

Generated by `analysis/make_failure_map.py` from existing claims/results only -- no new runs. Regenerate after any
new memory-boundary measurement lands (`py -3.12 analysis/make_failure_map.py` prints the same table this file
holds, from the same hardcoded evidence table, so the two stay in sync by construction until a real automated
evidence-scan replaces the hardcoded table).

Outcome vocabulary: **HARD_FAIL** (the runtime refuses to start or errors out with a clear message), **SILENT_SPILL**
(memory spills past its budget -- to system RAM, unified memory paging, or a driver-level fallback -- with a
latency/throughput cost but no error), **SILENT_TRUNCATION** (the prompt or context is silently cut, no error),
**CRASH** (the process dies, e.g. device-lost or an unhandled exception), **HANG** (the process stops responding
with no error and no crash), **NOT_MEASURED** (no existing data covers this cell).

## Cross-vendor contrast this table already shows (existing data only)

The one real cross-vendor comparison the current data supports is `-ngl 99` pinned, full-GPU-layers, past the memory
budget: **Intel Vulkan HARD_FAILs (a clear driver error), NVIDIA CUDA SILENT_SPILLs (a driver-level fallback with a
latency cost and no error)**. Same failure trigger (forced full GPU residency past the memory budget), two
completely different vendor-driver responses, on two different runtimes' most similar configuration. This is the
single most defensible existing cross-vendor claim in this table -- everything else in the grid is NOT_MEASURED and
needs new runs before it can be cited.
