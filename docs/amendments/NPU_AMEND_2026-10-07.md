## 1. Load key

The runner passes MAX_PROMPT_LEN=<setting> and MIN_RESPONSE_LEN=8 in the
LLMPipeline config. 8 is the runner's MAX_NEW_TOKENS. The runner no longer
passes NPUW_LLM_MAX_PROMPT_LEN. NPUW_LLM_PREFILL_CHUNK_SIZE is unchanged
(1024).

Evidence (run 2, request 2048): K-NPUW (NPUW_LLM_MAX_PROMPT_LEN=2048)
refused the ~1500 prompt; the runtime said the limit was 1024. K-DOC
(MAX_PROMPT_LEN=2048, MIN_RESPONSE_LEN=8) accepted 1508 tokens and
refused 2133 tokens; the runtime said the limit was 2048.

## 2. Realized-capacity check replaces the readback

On openvino-genai 2026.2.1, LLMPipeline has no get_property. So the
runner's readback (pipe.get_property, falling back to core.get_property)
can only return the device default, 1024. Runs 1 and 2 recorded this:
the readback was 1024 from the core fallback in all four arms, including
the arm that applied 2048. "Readback == request" therefore cannot show
that a setting applied.

After every int4 load, before the canary arms and before any timed
generate, the runner sends two probes on the loaded NPU pipeline:

- P1: a prompt of cap - 64 realized tokens. It must be accepted (generate
  returns), with pipeline_input_tokens == the realized count, and valid
  (parses with the GPU parser; repeated 4-gram share not above 0.5, per
  docs/NPU_PROTOCOL.md).
- P2: a prompt of cap + 64 tokens sent. It must be refused by the runtime
  length check: generate raises, and the message contains
  "input_ids.get_size() <= m_max_prompt_len".

If either probe fails, the session is REFUSED_CAPACITY. The probe records
are written to the summary and nothing is timed. Probes are not timings
and are not rungs. They also run in load-only sessions.

This replaces "readback == request" as the way prediction (a) is
operationalized: "loads at the requested value" now means the load
succeeds and both probes pass at the requested value. The device-default
readback is still recorded, as information only, and gates nothing. The
prediction text in NPU1_PREREG.json is not edited.

## 3. Single chat template

Every NPU and GPU generate in the NPU-1 runner uses
apply_chat_template=False (as the GPU measurement paths already do) and
the list call form, generate([prompt], ...). The prompt is already
rendered by seam.tools.boot4_text.rendered_exact_prompt. prompt_length is
the pipeline-reported input count, DecodedResults.perf_metrics
.get_num_input_tokens(). A generate that returns without that count is
not timed (reason prompt_length_not_reported).

Reason: the runner applied the template twice. GenerationConfig defaults
to apply_chat_template=True, and the runner sends an already-rendered
prompt. That adds 8 tokens. Evidence: in run 1 the runtime said "1508 is
passed" for 1500 realized tokens; in run 2, pipe_in = realized + 8 for
every accepted prompt. A CPU check off the NPU
(derived/npu/diag/NPU_MAXLEN_DIAG_RULE_V2.md) showed 26 vs 18 tokens.
The runner's recorded prompt_length did not show this. It fell back to
the requested n, because a str input returns no perf_metrics.

## 4. Ladder

Order: the guarded 1024 rerun first (item 3 changes the workload), then
2048, 4096, 8192, then 16384 load-only. One detached session per setting,
as before. The SLO (10 s TTFT), bisection low 64 and resolution 64,
repeats, the validity rule, the GPU canary guard (2026-10-05 amendment),
and the binding definitions (TOOLCHAIN_CAP, LATENCY, LOAD_FAIL) are
unchanged. REFUSED_CAPACITY is a refusal, not a binding.
